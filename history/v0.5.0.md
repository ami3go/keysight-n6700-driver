# v0.5.0 — 2026-09-14

## Objective

Close the specific structural gap keeping this driver from LPDS-001 §9's
`stable` bar: "LPDS-019 conformance passes against real hardware."

## Source baseline

Builds on v0.4.0 (`keysight-n6700-driver`), no repository restructure.

## What was built

`tests/conformance/test_driver_call_protocol_conformance.py` asserts the
exact outbound SCPI text via `ScriptedScpiTransport.history` — a
simulator-only recording feature no real VISA/TCP transport exposes, so
that suite structurally cannot run against real hardware as written.

`tests/hardware/test_hardware_protocol_conformance.py` realizes the same
`tests/conformance/data/protocol_vectors.yaml` vectors against real
hardware instead, using `connect(protocol_trace=RecordingTraceObserver())`
(LPDS-008 tracing) to capture real outbound bytes at the transport boundary
in place of the simulator's history. `tests/conformance/checks.py` was
extracted so both suites share the same pass/fail logic (return-type/value
checking) and cannot silently diverge on what "a vector passes" means.

Vectors that don't apply to real hardware are skipped with a specific,
visible reason rather than silently dropped or faked: `connect-simulated`
and `set-load-mode` (simulator-only `SIM:LOAD:*` syntax) always skip;
`set-smu-mode`/`get-smu-mode` skip if no real SMU module is discovered.
Every other vector's channel number is remapped from the simulator's
default map (channel 1 = power supply, channel 2 = SMU) onto whatever
channel the real mainframe actually has that module type on.
`reset-device` (`*RST`) and `enable-output` are gated behind their own
explicit signals (`N6700_HIL_PROTOCOL_ALLOW_RESET`/
`N6700_HIL_PROTOCOL_OUTPUT_CONFIRM`) since they reset the whole instrument
or energize a real output respectively.

## What was run

Against the real N6700C at 192.168.0.6: **18 of 24 vectors passed** in the
default configuration; a 19th (`enable-output`) passed when its explicit
confirmation was given. The remaining 5: 2 are permanently simulator-only
by design, 2 need a real SMU module this mainframe doesn't have, and 1
(`reset-device`) was deliberately not exercised (opt-in, not asked for).

This surfaced two real, vector-specific findings, both real-hardware-test
fixes, not driver bugs:

- `get_identity()`'s vector expected `"KEYSIGHT TECHNOLOGIES"` (the
  simulator's fixed uppercase fake identity); the real N6700C answers
  `"Keysight Technologies"` (title case). The driver's own manufacturer
  validation (`driver.py`'s `_validate_identity`) already normalizes case
  before comparing, so the real-hardware check now does too.
- `channel_count()`'s vector expected `4` (the simulator's fixed fixture
  topology); the real mainframe reports `2`, the number of modules actually
  installed. Checked for type/positivity on real hardware, not exact
  equality.
- `channel_count()`'s expected outbound command wasn't found on some runs:
  it caches its result per session, and the shared real-hardware connection
  already triggered it once via `connect()`'s own `discover_modules()`
  before the vector ran. Checked against the whole session's trace for this
  one vector, not just "since this call."

## Public API impact

None. This is test infrastructure; no driver source file changed.

## Test/evidence summary

228 tests pass against the simulator (unchanged), plus 24 new parametrized
real-hardware vector tests (skipped without `N6700_HIL_*`); `ruff` and
`mypy --strict` clean. Final hardware state independently verified after
the real run: both channels off, error queue empty.

## Known limitations

Driver status remains `untested` (LPDS-001 §9), not `stable` — this
release provides real LPDS-019 evidence for the power-supply/electronic-
load path specifically, but a real SMU module, protection-trip/clear
behavior, and remote/local control remain simulator-only. See
[`review/known_risks.md`](../review/known_risks.md).
