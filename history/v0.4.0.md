# v0.4.0 — 2026-09-14

## Objective

Read the official Keysight N6705C User's Guide / Programmer's Reference for
the N6791A module (provided by the user in `Keysight_documents/`) and fix
the driver's electronic-load support, which v0.3.1 had gotten half right
from real-hardware probing alone.

## Source baseline

Builds on v0.3.1 (`keysight-n6700-driver`), no repository restructure.

## What the manual corrected

v0.3.1 found that a real `N6791A` answers `VOLT?`/`CURR?`/`MEAS:VOLT?`/
`MEAS:CURR?`/`OUTP?` like a power-supply channel but never replies to
`FUNC:MODE?`, and classified it as `power_supply` to avoid ever sending that
query again. The official documentation shows this was an incomplete
diagnosis: `N6791A`/`N6792A` (`N679xA`) are genuine **Electronic Load
Modules** (100W/200W), not power supplies, with four priority modes
(voltage/current/resistance/power). `FUNC:MODE` was never a valid N6700
command for *any* module family — the real command is plain `FUNCtion`,
which takes two arguments (`CURRent`/`VOLTage`) for the N678xA SMU and four
(`CURRent`/`VOLTage`/`RESistance`/`POWer`) for N679xA. The load's input
terminals are switched with the ordinary `OUTP` command; the manual
explicitly notes the load's input is called "Output" throughout.

## Fixed

- `module_capabilities.py`: `N679x` reclassified from `power_supply` to
  `electronic_load` (`LOAD_PREFIXES`, replacing the empty
  `VERIFIED_LOAD_MODELS` allowlist), with `verified_real_load_commands=True`
  and all four `supports_load_cc/cv/cr/cp` flags set.
- `channel.py`: `ElectronicLoadChannel` now implements the real N679xA
  command set — `FUNC CURRent|VOLTage|RESistance|POWer` for priority mode,
  `VOLTage`/`CURRent`/`RESistance`/`POWer` for the corresponding level,
  `OUTP` for input on/off, and `CURRent:LIMit` for the current limit
  available in non-current-priority modes — alongside `configure_cv`/
  `configure_cr`/`configure_cp` convenience methods (`configure_cc` already
  existed). `SIM_LOAD`'s simulator-only `SIM:LOAD:*` placeholder path is
  unchanged.
- `channel.py`: `SMUChannel.set_smu_mode`/`get_smu_mode` fixed from
  `FUNC:MODE` to plain `FUNC` — the same bug as the load module, just never
  noticed because no real SMU has been hardware-tested yet.
- `simulator.py`: updated to match (`FUNC`/`FUNC?` instead of
  `FUNC:MODE`/`FUNC:MODE?`, now accepting all four priority values; added
  generic `RES`/`POW`/`CURR:LIM` read/write so the simulator can stand in
  for a real N679xA-classified channel in tests).
- `modules.py` and `driver.py`'s `DriverMetadata.supported_models` updated
  to describe `N679xA` as an Electronic Load Module family.

## Public API impact

`ElectronicLoadChannel.set_input`/`get_input`/`set_load_mode`/
`get_load_mode`/`set_load_current`/`set_load_voltage`/`set_load_resistance`/
`set_load_power` (and their getters) now send different SCPI for any
real (non-`SIM_LOAD`) load module than before — previously they either
raised `DriverUnsupportedOperationError` unconditionally (no real model was
ever accepted) or were unreachable. New: `set_load_current_limit`/
`get_load_current_limit`, `configure_cv`/`configure_cr`/`configure_cp`.
`classify_module("N679xA-prefixed model")` now returns `module_type=
"electronic_load"` instead of `"power_supply"` — any caller that had
started depending on the v0.3.1 `power_supply` misclassification (unlikely,
since it was one day old) would need to switch to `driver.load(channel)`
instead of `driver.power_supply(channel)`.

## Test/evidence summary

228 tests pass against the simulator, 12 skipped (HIL tests without real
hardware attached) (`ruff` and `mypy --strict` clean),
including new coverage in `tests/unit/test_electronic_load_channel.py`
(priority-mode/level/input command generation against a real-capabilities
N679xA object driven through the simulator) and a new
`test_smu_channel_current_priority` regression test. The corrected
`N6791A` classification and the `FUNC` (not `FUNC:MODE`) command have not
yet been re-run against real hardware; only the original v0.3.1 read-only
probe against `N6791A` (which never actually depended on `FUNC:MODE`
succeeding) remains as real-hardware evidence for the query side. A new
read-only hardware test, `test_every_electronic_load_channel_reports_mode_
and_measurements`, is ready in `tests/hardware/test_hardware_acceptance.py`
for the next real-hardware run.

## Known limitations

The N679xA electronic-load *write* path (priority mode selection, level
setpoints, input on) has not been run against real hardware — only
read-only queries have real-hardware evidence. The guarded output test
still has never been run against real hardware, and no run so far has
included a genuine SMU module. See
[`review/known_risks.md`](../review/known_risks.md).
