# v0.3.0 — 2026-09-14

## Objective

Add the tooling to check the driver's API against real hardware, closing
the "nobody has built this yet" part of the biggest gap in
`review/known_risks.md`. The gap itself — no real hardware has actually
been run against — cannot be closed without a physical instrument; this
release makes doing so a matter of plugging one in and running a command.

## Source baseline

Builds on v0.2.0 (`keysight-n6700-driver@c898bb2`), no repository restructure.

## Added

- `scripts/run_hardware_self_check.py` — connects to a real N6700
  (`--resource`, required; `--connection-type`, `--port`), runs every
  read-only capability (identity, connection state, capability/configuration
  introspection, self-test, error queue, module discovery, and per-channel
  model/serial/options/measurement/setpoint-readback/status queries, branched
  by module type), and writes `results/hardware_self_check/<timestamp>/
  {report.json,summary.md}`. `--output-test` plus all three of
  `--output-channel`/`--output-voltage`/`--output-current-limit` (no
  defaults) additionally runs one guarded enable/measure/disable cycle on a
  single power-supply/SMU channel, refusing to run if that channel is
  already energized, requiring a typed `yes` (or `--yes`) first, and always
  disabling the output again in a `finally` block plus a `safe_shutdown()`
  second net.
- `tests/hardware/` (`conftest.py`, `test_hardware_acceptance.py`) — the
  same coverage as individually-reported pytest tests. Gated by
  `N6700_HIL_ENABLED=true` + `N6700_RESOURCE` (skipped otherwise, via an
  autouse package-scoped fixture) for the read-only tests, plus
  `N6700_HIL_OUTPUT_TEST_ENABLED`, `N6700_HIL_OUTPUT_CHANNEL`,
  `N6700_HIL_OUTPUT_VOLTAGE`, `N6700_HIL_OUTPUT_CURRENT_LIMIT`, and
  `N6700_HIL_OUTPUT_CONFIRM=yes` (five separate signals) for the guarded
  output test.
- `docs/hardware_acceptance_tests.md` — full reference for both tools,
  linked from `docs/index.md` and the top-level README.
- `tests/unit/test_hardware_self_check_script.py` — loads the script as a
  module and drives its checking/reporting functions directly against
  `N6700.connect_simulated()`. This is the only verification this release
  got: no real N6700 was available to run either tool against for real.

## Public API impact

None. Both additions are test/tooling surfaces, not driver API.

## Test/evidence summary

225 tests pass against the simulator (11 hardware tests correctly skip by
default without `N6700_HIL_ENABLED`/`N6700_RESOURCE`); `ruff` and
`mypy --strict` clean, including the new script.

## Known limitations

Unchanged in substance from v0.2.0 — see
[`review/known_risks.md`](../review/known_risks.md). The "no real hardware
run" gap now has tooling to close it, but the run itself still hasn't
happened.
