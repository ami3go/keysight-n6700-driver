# v0.3.1 — 2026-09-14

## Objective

Run `scripts/run_hardware_self_check.py` for the first time against a real
N6700, and fix whatever it found — the exact next step
`review/known_risks.md` called for after v0.3.0.

## Source baseline

Builds on v0.3.0 (`keysight-n6700-driver@a17803b`), no repository restructure.

## What was run

Read-only checks against a real N6700C mainframe at 192.168.0.6
(firmware E.02.09.3271, serial MY56320259), two installed modules:
channel 1 a power-supply-family module, channel 2 an `N6791A`.

First run: 8 passed, 4 failed (self-test timed out at the 5s default,
faulted the transport, and every later check failed cleanly rather than
hanging — correct behavior, but it meant nothing past that point got
checked). Second run, timeout raised to 60s for diagnosis: 35 passed, 0
failed, 1 skipped (`channel[2].typed_queries`, correctly skipped because
`N6791A` wasn't a recognized module family). Direct read-only probing of
channel 2 (`MEAS:VOLT?`, `VOLT?`, `MEAS:CURR?`, `CURR?`, `OUTP?` all
succeeded; `FUNC:MODE?` never replied and faulted the connection) confirmed
it behaves as a power-supply channel, not an SMU. Final run after the
fixes below: **43 passed, 0 failed, 0 skipped.**

## Fixed

- `scripts/run_hardware_self_check.py`'s `--timeout-s` default and
  `tests/hardware/conftest.py`'s new `N6700_TIMEOUT_S` both changed from
  deferring to the transport's 5s default to defaulting to 15s, with the
  real `*TST?` timing (~5.4s) as the documented justification.
- `module_capabilities.py`: `POWER_PREFIXES` now includes `N679x`
  (previously unrecognized, fell to `unknown`). Classified as
  `power_supply`, deliberately not `smu` — `FUNC:MODE?` must never be sent
  to this family. `modules.py`'s `SUPPORTED_MODULE_FAMILIES` and
  `driver.py`'s `DriverMetadata.supported_models` updated to match.
  `tests/unit/test_module_capabilities.py` added as a regression guard.

## Public API impact

None. `classify_module()`'s behavior changed only for previously-`unknown`
`N679x` models, which had no typed capability before this and would have
raised `DriverUnsupportedOperationError` on any typed accessor.

## Test/evidence summary

228 tests pass against the simulator (unchanged from v0.3.0 plus the new
regression test); `ruff` and `mypy --strict` clean.
`results/hardware_self_check/` holds the three real-hardware run reports
this release is based on (gitignored, not committed — see the run
descriptions above for what they showed).

## Known limitations

Unchanged in substance — see [`review/known_risks.md`](../review/known_risks.md).
The guarded output test has still never been run against real hardware, and
no run so far has included a genuine SMU (`N678x`) or electronic-load
module, so those remain simulator-only.
